## 6. The reference tie construction

Constants are the LilyPond Tie grob defaults `height-limit = 1.0 sp`, `ratio = 0.333` (`scm/define-grobs.scm`, v2.26.0), converted through `tieRefStaffSpace = 4.984pt`. ## 7. Prepared real-engine studio

The studio's two views are now **engraved ahead of time** by the real engine in a Node context; the browser runs a thin viewer that never imports or runs the engine, the linter or a score builder.

- `src/render/janko/prepared/generate.ts` — pure deterministic generator: both view panels from `renderCandidatesView`/`renderReferenceView` on `createStudioConfig()`, plus the primary score's lint facts from the real linter; content hashes (`sha256`) over artifact bytes and deterministic status facts (the measured lint wall-time is reported but never hashed).
- `src/render/janko/prepared/vite-plugin.ts` — the Vite seam. Dev: a virtual manifest module (`virtual:janko-prepared-manifest`) plus a middleware serving artifacts from memory at `/@janko-prepared/<sha256>.html`; watched inputs (`src`, `data`, `public/midi`, `package*.json`) are coalesced and serialized through a generation queue; every generation re-fingerprints its inputs and publishes only a **coherent** snapshot (moved inputs → retry, then stale); failures keep the last coherent output labelled **stale** with the error; the actual HMR protocol delivers a `js-update` whose `path` is the **accept-owner** — the client module that imported and accepted the manifest, found in the client module graph through `acceptedHmrDeps` — and whose `acceptedPath` is the manifest module's own URL (the exact string the import-analysis overwrite records in the viewer's accept deps). Addressing the update to the virtual module's own URL reaches no callback at all (the client keys its callbacks by the owner path) — that was the silent staleness the first implementation suffered, and it is pinned by the real-server protocol test. Build: `buildStart` generates once and emits content-addressed assets `janko-prepared/<sha256>.html`; the manifest references them with relative `new URL('../janko-prepared/<hash>.html', import.meta.url)` expressions — correct under the repo's `'./'` base and nested GitHub Pages paths; a generation failure fails the build.
- **Config-graph isolation (Round 49 correction)**: the generator and its whole transitive chain (studio, engine, scores, linter) are loaded **lazily per generation** through Vite's own `runnerImport` pipeline, and the pure delivery seam lives in `src/render/janko/prepared/seam.ts`. `loadConfigFromFile` on the real config reports the dependency set `{vite.config.ts, prepared/vite-plugin.ts, prepared/seam.ts}` — an engine/score/model edit triggers an in-place prepared regeneration, never the config-dependency server restart (verified live: an `engine.ts` touch produces no "restarting server" line).
- `src/render/janko/prepared/viewer.ts` — the thin browser shell: imports only `../studio-session` (shared tabs/zoom/scroll session), `./viewer-dom` (the DOM application layer) and the manifest module. Explicit states — `preparing`, `ready`, `stale`, `error` — never blank; out-of-order artifact fetches are dropped by generation id; HMR accepts the manifest **by id** and re-applies in place, preserving the selected tab, zoom and scroll place (the applier re-shows the session view on the swapped panels before the place restore). Every handler it installs is detached on re-mount.
- `src/render/janko/prepared/viewer-dom.ts` — the DOM application primitives (live-collecting `showView`, `selectStudioView`, the manifest state machine `createPreparedApplier`): pure DOM, no virtual import and no engraving module, so the exact shipped switch/apply code is testable against a swap-simulating DOM (`test/janko-prepared-viewer.test.ts`).
